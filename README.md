# nostr-notify

A drop-in replacement for cron/server digest emails using [Nostr](https://nostr.com) as the delivery transport. Pipe any command output to it and it arrives as an encrypted NIP-17 direct message in your Nostr client.

```sh
df -h | nostr-notify --subject "disk usage: $(hostname)"
```

## What it does

Machines running periodic jobs (backups, log summaries, monitoring scripts) traditionally send their output by email. `nostr-notify` replaces that SMTP hop with a Nostr DM:

- Output is delivered as an end-to-end encrypted [NIP-17](https://github.com/nostr-protocol/nips/blob/master/17.md) direct message
- Each message is gift-wrapped ([NIP-59](https://github.com/nostr-protocol/nips/blob/master/59.md)) with a fresh ephemeral key and a randomised timestamp — timing metadata is hidden from relays
- Each machine sends from its own dedicated keypair
- Delivery succeeds if any one configured relay accepts the event; all relays are tried in parallel
- On complete failure the tool exits non-zero, which triggers whatever alerting your cron setup already uses

## Requirements

- A Nostr relay that supports NIP-17 gift-wrap (kind:1059). [Haven](https://github.com/barrydeen/haven) works well; public relays such as `relay.damus.io` and `nos.lol` also accept gift-wrapped events.
- NTP running on every machine — Nostr events include a timestamp and relays reject events that are too far from the current time.
- Go 1.23+ to build. No runtime dependencies on target machines; the output is a static binary.

## Quick start

### 1. Generate a service keypair

Each machine that sends notifications needs its own keypair:

```sh
nostr-notify keygen
```

This writes `./service.nsec` (mode 0600) and prints the corresponding `npub` to stdout:

```
npub1abc...
keypair written to ./service.nsec
add this npub to your Haven whitelist so the service key can publish:
  npub1abc...
```

The key file looks like this — the `npub` comment is for your reference:

```
# npub: npub1abc...
nsec1xyz...
```

Protect the file: `chmod 600`, owned by the user that runs your cron jobs.

### 2. Create a config file

Copy the example config and fill in your details:

```sh
# System-wide (all users on this machine)
sudo mkdir -p /etc/nostr-notify
sudo cp config.example.toml /etc/nostr-notify/config.toml
sudo $EDITOR /etc/nostr-notify/config.toml

# Or per-user
mkdir -p ~/.config/nostr-notify
cp config.example.toml ~/.config/nostr-notify/config.toml
$EDITOR ~/.config/nostr-notify/config.toml
```

Minimal working config:

```toml
[identity]
key_file = "/etc/nostr-notify/service.nsec"

[recipient]
pubkey = "npub1..."   # your Nostr public key

[relays]
urls = [
  "wss://relay.damus.io",
  "wss://nos.lol",
]
```

### 3. Whitelist the service npub (if using Haven)

If your relay runs Haven, add the npub printed by `keygen` to the whitelist config so the service key is allowed to write. No social-graph follows needed.

If you use only public relays, skip this step.

### 4. Send a test message

```sh
echo "nostr-notify is working" | nostr-notify --subject "test from $(hostname)"
```

Exit 0 means at least one relay accepted the event. Check your Nostr client.

## Configuration

### Config file locations

The tool searches these paths in order and uses the first one found:

| Path | Purpose |
|---|---|
| `~/.config/nostr-notify/config.toml` | Per-user config (takes precedence) |
| `/etc/nostr-notify/config.toml` | System-wide config |

If no config file is found the tool runs in flag-only mode (useful during development). A file that exists but contains invalid TOML is a hard error.

### Config file reference

See [`config.example.toml`](config.example.toml) for a fully annotated example. The fields active today:

```toml
[identity]
# Path to the nsec file generated by `nostr-notify keygen`.
# Mode 0600, owned by the user running the cron jobs.
key_file = "/etc/nostr-notify/service.nsec"

[recipient]
# Your Nostr public key (npub1... or hex).  Required — no built-in default.
pubkey = "npub1..."

[relays]
# All relays are tried in parallel; delivery succeeds if any one returns OK.
# NIP-59 gift-wrap means the content is encrypted — safe to use public relays.
urls = [
  "wss://relay.damus.io",
  "wss://nos.lol",
]
```

Sections `[delivery]` (retry, spool) and `[logging]` are accepted in the file but not yet active; see `config.example.toml` for their planned fields.

### Value resolution order

For each setting, the tool applies this priority:

```
CLI flag  >  config file  >  built-in default
```

| Setting | CLI flag | Config key | Built-in default |
|---|---|---|---|
| Service key | `--key-file` | `identity.key_file` | `./service.nsec` if present |
| Recipient | `--to` | `recipient.pubkey` | none — required |
| Relay list | `--relays` | `relays.urls` | 5 public relays |
| Subject | `--subject` | — | `hostname YYYY-MM-DD` |
| Format | `--format` | `message.format` | `plain` |

### Default relay list

When no relay list is provided by config or flag, the tool falls back to a set of well-known public relays that accept NIP-59 gift-wrap events:

- `wss://relay.damus.io`
- `wss://relay.nostr.band`
- `wss://nostr.mom`
- `wss://relay.primal.net`
- `wss://relay.snort.social`

Private or self-hosted relays belong in your config file.

## Usage

```
nostr-notify [flags]
nostr-notify keygen [--key-file PATH]
nostr-notify sendmail [sendmail-flags] [recipients...]
```

### Flags

| Flag | Description |
|---|---|
| `--subject TEXT` | Message subject line (default: `hostname YYYY-MM-DD`) |
| `--to NPUB` | Recipient public key — overrides config |
| `--key-file PATH` | Path to service nsec file — overrides config |
| `--file PATH` | Read message body from file instead of stdin |
| `--relays URLS` | Comma-separated relay URLs — overrides config |
| `--format plain\|code` | `plain` sends body as-is (default); `code` wraps in a fenced Markdown code block |
| `--content-limit N` | Truncate message body at N bytes (default: 65536) |
| `--debug` | Print debug logs to stderr |

### Send a message

```sh
# Pipe stdin
some-command | nostr-notify --subject "daily digest: $(hostname)"

# Read from a file
nostr-notify --subject "backup report" --file /var/log/backup.log

# Override recipient for a one-off
some-command | nostr-notify --to npub1...

# Override relays
some-command | nostr-notify --relays "wss://relay1.example.com,wss://relay2.example.com"
```

### Generate a keypair

```sh
nostr-notify keygen [--key-file PATH]
```

Generates a new keypair, writes the nsec to PATH (default: value from config, or `./service.nsec`), mode 0600. Refuses to overwrite an existing file. Prints the npub to stdout.

### Intercept system mail (sendmail mode)

`nostr-notify sendmail` reads a raw RFC 2822 email from stdin and delivers it as a Nostr DM. It accepts and ignores the flags and recipient arguments that cron and system daemons pass to sendmail (`-oi`, `-t`, `root`, etc.), so it is a transparent hook into the existing mail flow.

Add it to root's `.forward` file — the `\root` line keeps local delivery intact, and the pipe line sends a copy to Nostr:

```
\root
"|/usr/local/bin/nostr-notify sendmail"
```

Works the same on Ubuntu (postfix) and OpenBSD (OpenSMTPD). No system-wide MTA config needed.

Alternatively, via `/etc/aliases`:

```
root: root, "|/usr/local/bin/nostr-notify sendmail"
```

Then run `newaliases` (Ubuntu) or `doas newaliases` (OpenBSD) to rebuild the alias database.

## Cron integration

Replace `mail` or `sendmail` in your cron job output line:

```
# Before
0 3 * * * root /usr/local/bin/backup.sh 2>&1 | mail -s "backup $(hostname)" you@example.com

# After
0 3 * * * root /usr/local/bin/backup.sh 2>&1 | nostr-notify --subject "backup $(hostname)"
```

With a config file at `/etc/nostr-notify/config.toml`, no flags are needed at all. Non-zero exit from `nostr-notify` (all relays failed) is treated as a cron error and will fall back to emailing root — so delivery failures are visible rather than silent.

## Platform notes

### OpenBSD

- Use `doas` instead of `sudo`
- Store config at `/etc/nostr-notify/config.toml` and key at `/etc/nostr-notify/service.nsec`, owned `root:wheel`, mode `0600`
- The default `PATH` in cron is restricted; use the full path `/usr/local/bin/nostr-notify`
- Build with `GOOS=openbsd GOARCH=amd64` from any Go toolchain (see Makefile)

### Ubuntu / Debian

- Store config at `/etc/nostr-notify/config.toml` and key at `/etc/nostr-notify/service.nsec`, owned `root:root`, mode `0600`
- For non-root cron users, adjust file ownership accordingly

## Architecture

`nostr-notify` implements the full [NIP-17](https://github.com/nostr-protocol/nips/blob/master/17.md) + [NIP-59](https://github.com/nostr-protocol/nips/blob/master/59.md) gift-wrap flow:

```
kind:14 rumor  (unsigned — your message content)
  → NIP-44 encrypt with sender key  → kind:13 seal  (signed by service key)
  → NIP-44 encrypt with ephemeral key  → kind:1059 gift wrap  (published to relays)
```

- Seal and gift wrap each get a random `created_at` up to 2 days in the past (NIP-59 timing privacy)
- A fresh ephemeral keypair is generated for every message
- NIP-42 AUTH is performed on each relay connection
- All configured relays are attempted in parallel; exit 0 if any one succeeds

External dependencies: [`github.com/nbd-wtf/go-nostr`](https://github.com/nbd-wtf/go-nostr), [`github.com/BurntSushi/toml`](https://github.com/BurntSushi/toml).

### AUTH flow note

go-nostr processes relay messages in a background goroutine. Haven sends the NIP-42 AUTH challenge on connect; after a brief pause we attempt a proactive AUTH. If the relay still replies `auth-required:` on the publish attempt, we authenticate with the fresh challenge and retry once. This handles both relays that challenge on connect and those that challenge on publish.
